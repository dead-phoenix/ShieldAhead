# ShieldAhead Technical Data Flow

This document explains the actual code path from user input in the React frontend to the final JSON response generated by the Flask backend. It is written as a code-review handoff rather than a product summary.

## 1. Runtime Architecture

```text
Browser
  |
  | React/Vite frontend
  | localhost:5173
  v
fetch("http://127.0.0.1:5001/api/wifi?postcode=3064")
  |
  | HTTP + JSON
  v
Flask backend
  |
  | app.py registers blueprints
  | routes receive requests
  v
Local PostgreSQL or Neon PostgreSQL
  |
  | If stored data is missing/stale:
  v
External providers
  - VicFreeWiFi
  - Vicmap
  - ACNC
  - Photon/Nominatim geocoding
```

Production Docker builds the frontend first and copies `frontend/dist` into the backend image. The backend then serves the SPA and API from the same deployed origin.

## 3. User Input: Location Page

The main input starts in [ChooseLocationPage.tsx](../frontend/src/features/location/pages/ChooseLocationPage.tsx).

### Manual input

The user enters a value into the controlled React input:

```tsx
const [query, setQuery] = useState(currentPostcode)

<input
  id="location-query"
  value={query}
  onChange={(event) => setQuery(event.target.value)}
/>
```

The input value is held in the browser as the React variable `query`.

When the form is submitted:

```tsx
const parsed = parseManualLocationQuery(query)
```

The result is one of:

```ts
{ kind: 'postcode', postcode: '3064' }
```

or:

```ts
{ kind: 'place', query: 'Craigieburn' }
```

The page resolves the input and eventually calls:

```tsx
await finish(resolved.postcode, resolved.label)
```

`finish()` saves the search location in browser localStorage and navigates to either `/wifi` or `/support`.

```tsx
saveSearchLocation({ postcode, label })
navigate(destination === 'support' ? appRoutes.support : appRoutes.wifi, {
  state: { searchPostcode: postcode, searchUpdatedAt: Date.now() },
})
```

The household postcode is not sent to the backend at this point. It is sent later when the Wi-Fi or support page creates its API request.

## 4. Exact Wi-Fi Frontend Request Chain

For a user searching postcode `3064`:

```text
WifiListPage.tsx
  -> getWifiRepository('3064')
  -> createApiWifiRepository({ postcode: '3064' })
  -> repository.list()
  -> resolveApiUrl(..., '/api/wifi', '3064')
  -> fetch(URL)
```

### Step 1: page obtains postcode

[WifiListPage.tsx](../frontend/src/features/wifi/pages/WifiListPage.tsx) reads the navigation postcode first and localStorage second:

```tsx
const navigationPostcode = routeLocation.state?.searchPostcode
const postcode = typeof navigationPostcode === 'string'
  ? navigationPostcode
  : getSearchPostcode()
```

Then it creates the repository:

```tsx
const repository = useMemo(
  () => getWifiRepository(postcode),
  [postcode],
)
```

### Step 2: repository factory

[wifiRepository.ts](../frontend/src/data/wifiRepository.ts) receives the string:

```ts
getWifiRepository(postcode: string)
```

It passes that value into the API repository:

```ts
createApiWifiRepository({
  baseUrl: import.meta.env.VITE_API_BASE_URL ?? '',
  postcode,
  timeoutMs,
})
```

### Step 3: repository list method starts request

[apiWifiRepository.ts](../frontend/src/data/api/apiWifiRepository.ts) stores `postcode` in the repository closure. When `list()` runs:

```ts
const url = resolveApiUrl(baseUrl, '/api/wifi', postcode)
```

### Step 4: URL is constructed

[resolveApiUrl.ts](../frontend/src/data/api/resolveApiUrl.ts) does:

```ts
const url = new URL(path, `${origin}/`)
url.searchParams.set('postcode', postcode)
return url
```

For local development:

```text
baseUrl = http://127.0.0.1:5001
path = /api/wifi
postcode = 3064
```

The final URL is:

```text
http://127.0.0.1:5001/api/wifi?postcode=3064
```

### Step 5: browser sends HTTP request

The adapter calls the browser Fetch API:

```ts
const response = await fetcher(url, {
  headers: { Accept: 'application/json' },
  signal: controller.signal,
})
```

This is the exact frontend/backend boundary. React does not import Python. The browser sends an HTTP request and Flask receives it.

## 5. Exact Flask Wi-Fi Input Handoff

`app.py` registers the Wi-Fi blueprint:

```py
app.register_blueprint(wifi_bp)
```

The blueprint is defined in [wifi_routes.py](../backend/routes/wifi_routes.py):

```py
wifi_bp = Blueprint("wifi", __name__)

@wifi_bp.route("/api/wifi")
def get_wifi():
```

When Flask receives:

```http
GET /api/wifi?postcode=3064
```

this line reads the frontend value:

```py
postcode = request.args.get("postcode", "").strip()
```

At this point:

```py
postcode == "3064"
```

This is the exact Python variable containing the user input.

The route then validates it:

```py
if not is_valid_vic_postcode(postcode):
    return jsonify({...}), 400
```

Then it converts the postcode to coordinates:

```py
user_lat, user_lng = postcode_to_coords(postcode)
```

The postcode is now represented in two ways:

```text
postcode = "3064"
user_lat = latitude for postcode 3064
user_lng = longitude for postcode 3064
```

## 6. How Wi-Fi Data Is Obtained

The Wi-Fi database does not contain a separate table for every postcode. `wifi_locations` is a shared source table containing Wi-Fi records from multiple areas.

The Wi-Fi route checks data in this order:

```text
1. In-process memory cache: _cache["data"]
2. PostgreSQL/Neon cache_meta row with key "wifi"
3. PostgreSQL/Neon wifi_locations table
4. External VicFreeWiFi and Vicmap providers only if no stored data exists
```

The database read happens here:

```py
if not all_records:
    db_meta = load_cache_meta("wifi")
    db_records = load_wifi_records_from_db()
```

`load_cache_meta("wifi")` reads freshness information from:

```sql
SELECT timestamp, freshness_status, removed_ids
FROM cache_meta
WHERE key = 'wifi';
```

`load_wifi_records_from_db()` reads the stored Wi-Fi source records:

```sql
SELECT * FROM wifi_locations;
```

If rows exist, they are converted from PostgreSQL row mappings into Python dictionaries by `_wifi_row_to_dict()`.

## 7. Why the Postcode Still Matters

After the statewide records are loaded, the requested postcode is used to calculate distance:

```py
for record in all_records:
    dist = haversine_km(
        user_lat,
        user_lng,
        record["latitude"],
        record["longitude"],
    )
    record["distanceKm"] = round(dist, 1)
```

Then the backend filters the records:

```py
within_radius = [
    record for record in all_with_distance
    if record["distanceKm"] <= SEARCH_RADIUS_KM
]
```

Therefore:

```text
Neon stores the shared Wi-Fi source dataset
  -> postcode 3064 becomes user_lat/user_lng
  -> distance is calculated to each stored record
  -> nearby records are returned
```

A Vicmap record may have an empty `postcode` field. It can still appear for postcode `3064` because its latitude and longitude place it inside the search radius.

## 8. Wi-Fi Backend Output

The route returns a Python dictionary through Flask:

```py
return jsonify({
    "records": all_records,
    "metadata": {
        "version": "1.1",
        "generatedAt": ...,
        "sourceName": ...,
        "coverageAreas": coverage,
        "limitations": limitations,
        "freshnessStatus": freshness_status,
    },
})
```

Flask serializes this dictionary into JSON. Example response shape:

```json
{
  "records": [
    {
      "id": "vicmap-20686",
      "name": "MICKLEHAM COMMUNITY CENTRE",
      "latitude": -37.59,
      "longitude": 144.72,
      "distanceKm": 3.8,
      "verificationStatus": "likely"
    }
  ],
  "metadata": {
    "sourceName": "VicFreeWiFi + Vicmap Features of Interest",
    "freshnessStatus": "current"
  }
}
```

## 9. Response Back to Frontend

The browser receives the HTTP response in `apiWifiRepository.ts`:

```ts
if (!response.ok) {
  throw new Error(...)
}

return normalizeWifiDataset(await response.json())
```

`normalizeWifiDataset()` checks the response contract:

- `records` must be an array.
- Every record must have a valid `id`, `name`, and `dataUpdatedAt`.
- Numbers must be finite.
- Missing optional values become `undefined`.
- Missing arrays become empty arrays.

Then `useRepositoryData()` receives the resolved promise:

```ts
load().then((result) => {
  if (isCurrent) setData(result)
})
```

React re-renders `WifiListPage` using:

```tsx
data.records
```

The visible list is then sorted by distance and limited for display. Map records are created from records with valid latitude/longitude.

## 10. Support-Service Equivalent

The support path uses the same request boundary with different names:

```text
SupportServicesPage.tsx
  -> getSupportServiceRepository(postcode)
  -> createApiSupportServiceRepository({ postcode })
  -> resolveApiUrl(baseUrl, '/api/charities', postcode)
  -> fetch('/api/charities?postcode=3064&_refresh=...')
  -> charities_routes.py::get_charities()
```

Flask receives the support postcode using the same statement:

```py
postcode = request.args.get("postcode", "").strip()
```

The route checks:

```text
memory charity cache
  -> Neon cache_meta key postcode:3064
  -> Neon charities table filtered by postcode
  -> ACNC source if stored data is unavailable
```

Then it:

1. Filters relevant ACNC records.
2. Converts them into `SupportService` dictionaries.
3. Geocodes street addresses.
4. Uses postcode coordinates as a fallback when address geocoding fails.
5. Calculates distance.
6. Returns JSON.

## 11. Checklist and Helpline Content

Helpline numbers and pre-crisis checklist definitions are served by the backend API from JSON files:

```text
backend/data/helplines.json
backend/data/pre_crisis_checklist.json
  -> GET /api/helplines and GET /api/checklist
  -> CrisisDetailPage.tsx
  -> crisisChecklistStorage.ts (tick state only)
  -> browser localStorage
```

The files are loaded into memory once at process start in
`services/crisis_content_service.py`. There are no Neon tables for this content.
Drop leftover empty tables with `backend/migrations/drop_helplines_and_checklist.sql`.

## 13. Developer Debug Checklist

When tracing a postcode request, inspect in this order:

1. Browser Network tab: confirm `/api/wifi?postcode=3064` or `/api/charities?postcode=3064`.
2. `WifiListPage.tsx` or `SupportServicesPage.tsx`: confirm the `postcode` variable.
3. Repository factory: confirm the same postcode is passed into the API adapter.
4. `resolveApiUrl.ts`: confirm the query parameter is present.
5. Backend route: inspect `request.args.get("postcode")`.
6. `db.py`: inspect `DATABASE_URL`, `cache_meta`, and table reads.
7. Route distance calculation: inspect `user_lat`, `user_lng`, and `distanceKm`.
8. Flask JSON response: inspect `records` and `metadata`.
9. Frontend normalizer: inspect contract validation.
10. React page: inspect `data.records` and rendered output.

The complete request boundary is:

```text
Frontend JavaScript variable
  -> URL query parameter
  -> HTTP request
  -> Flask request.args
  -> Python route variable
  -> database/cache/external provider
  -> Python dictionary
  -> Flask JSON
  -> JavaScript object
  -> React state
  -> rendered UI
```
